# Чек-лист паритета функций (v1)

Статус: в работе (Этап 0.5)
Обновлено: 2026-11-23
Связанные документы: [MIGRATION_PLAN.md](MIGRATION_PLAN.md), [DECISIONS.md](DECISIONS.md)

Чек-лист фиксирует функциональность текущего Vaadin-приложения, которую обязаны
повторить web SPA и Android-приложение до удаления Vaadin (Этап 4). Пока не все
пункты отмечены в обоих столбцах, паритет не достигнут.

## Как пользоваться

- Источник истины — текущее Vaadin-приложение на `dev` (экраны `PaymentsView`,
  `HistoryView`, `MediaView`, диалоги прогноза и разового платежа), с учётом
  исправлений из раздела «Известные пробелы».
- Один пункт = одно проверяемое действие или правило. Если поведение отличается
  между web и Android или от Vaadin — это баг, а не «особенность клиента».
- Отметка ставится после ручной проверки; автотесты (2.9, 3.7, 1.12) дополняют,
  но не заменяют ручной прогон.
- Формулировки «как в Vaadin» означают текущую семантику, а не идеальную.

**Готово, когда:** все пункты отмечены и для Web, и для Android, а регресс
Vaadin-экранов остаётся зелёным до Этапа 4.

## Известные пробелы текущего Vaadin-приложения

Паритет считается по **заявленному** поведению экрана, а не по текущим заглушкам.
Эти места нужно реализовать в API (задачи 1.8–1.9), иначе паритет недостижим.
Статус на 2026-11-16: пункты 1, 3, 5, 7, 10 закрыты; 2, 4 закрыты в API,
осталась локализация/пагинация в Vaadin UI.

1. **Медиа не загружается и не сохраняется.** `MediaView.loadMediaForAccount`
   и `MediaView.saveMediaItem` — `TODO`; `MediaService` умеет только читать по
   типу и удалять. Нужны create/update, чтение «всех», серверная валидация.
   **Исправлено:** API create/update, `MediaView` загружает и сохраняет через
   `MediaService`; `media(account_id, type)` больше не ограничивает список.
2. **Тип медиа в DTO не совпадает с UI.** `MediaMapper` отдаёт имена enum
   (`MOVIE`/`SERIES`), а `MediaView` использует русские подписи
   (`MediaType.getName()`). В API отдаём enum, локализация — на клиенте.
   **API готов:** enum в контракте; Vaadin сохраняет оба варианта, но колонка
   типа всё ещё показывает enum-имя.
3. **Новая строка правила без даты.** `createEmptyEditableItem` создаёт
   `nextDay = null`, но колонка `next_day` в БД `NOT NULL`. API обязан требовать
   дату и возвращать `400`. **Исправлено:** API требует дату, Vaadin ставит
   `nextDay = today`.
4. **История без пагинации.** Сейчас загружается весь список; контракт API
   предусматривает `page/size`, клиенты обязаны поддержать пагинацию.
   **API готов:** `page/size` и `totalElements`; Vaadin пока грузит всё.
5. **`IncomeDto` — форматированные строки.** В API отдаём числа и `LocalDate`,
   иначе Android/web будут парсить русские строки.
6. **Прогноз игнорирует просроченные правила.** Расчёт идёт с сегодняшнего дня,
   правила с `next_day < сегодня` не «догоняются». В v1 сохраняем текущую
   семантику; изменение — отдельной задачей после миграции.
7. **`ForecastCalculator` требует запись истории.** Если у счёта нет истории,
   возможен NPE. При создании счёта запись создаётся, но API должен явно
   обрабатывать отсутствие истории (`0`). **Исправлено:** прогноз, применение
   правила и баланс стартуют с `0`.
8. **Сумма правила: UI ограничивает `>= 0`, сервер — нет.** Для v1 нужно
   зафиксировать единое правило валидации (отрицательная сумма = доход) — вопрос
   к продукту; до решения сервер принимает целое число без ограничения, UI
   повторяет текущее ограничение.
9. **Создание счёта есть в сервисе, но не в UI.** В v1 счета доступны только на
   чтение, создание/переименование/удаление не входят в паритет.
10. **Статус медиа по умолчанию.** При `status = null` UI показывает
    «Ожидает просмотра»; сервер при создании должен проставлять
    `PLAN_TO_WATCH` явно. **Исправлено:** `MediaService.create` подставляет
    `PLAN_TO_WATCH`.
11. **Одноразовые правила и `end_date` не деактивируются после выполнения
    (C-14).** `RuleExecuteService.execute` сохраняет правило только когда
    следующий платёж изменился: для `Type.ONE.next()` возвращает `null`, условие
    `nextDay != null && !nextDay.isEqual(...)` ложно, поэтому запись не
    сохраняется и правило остаётся к оплате. Поле `active` было удалено миграцией
    `V5__drop_payment_rule_active.sql`, а `isRuleDue` в web ведёт себя так же.
    Это **общий пробел backend** (а не дефект Android): Android-столбец C-14
    осознанно не отмечен до исправления API. Побочный эффект в прогнозе:
    одноразовый платёж применяется повторно, и баланс прогноза расходится с
    историей (например, на счету 2 прогноз давал −1 554 ₽ против истории −777 ₽).
